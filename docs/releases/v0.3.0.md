# v0.3.0

Released 2026-10-26.

v0.3.0 still tracks `draft-hardt-oauth-aauth-protocol-11`,
`draft-hardt-httpbis-signature-key-09`, and `draft-hardt-aauth-bootstrap-02`.
The wire format is unchanged, so **v0.2 and v0.3 parties interoperate**.
v0.3 verifies more strictly, so it refuses some requests v0.2 accepted; see
[Security](#security).

## Upgrade

```sh
go get github.com/aauth-dev/aauth-go@v0.3.0
```

Go 1.26 or later, as for v0.2. Some APIs change, mostly in the server
packages: approvals carry the revision of the request shown, interaction
codes are looked up and then consumed at the person's decision, the
`ClaimsProvider` takes a request, and stores gain pruning and counting
methods. `AuthorizationHandler` requires `TrustIssuer`, and an agent
provider's `Domain` must be its issuer's host. The
[migration guide](https://github.com/aauth-dev/aauth-go/blob/main/MIGRATION.md#migrating-from-v02-to-v03)
lists every change with before and after code.

`accessserver.Client` now reports an access server's 402 Payment Required
as an error wrapping `*aauth.PaymentRequiredError` when no `Payment` handler
is configured.

## Highlights

- **Capabilities.** Agents say what they can handle with
  `AAuth-Capabilities` (`Transport.Capabilities`): involving the person,
  answering clarifications, or paying. Resources check `CanRaise` and
  `CanRequirePayment` before asking, so an agent is never left waiting for a
  person nobody will ask.
- **Access ahead of a call.** `Transport.Authorize` asks a resource's
  authorization endpoint for a scope before the first request, and caches
  the auth token or session token it gets. Resources serve the endpoint
  with `AuthorizationHandler`.
- **Payment.** A 402 Payment Required carries the payment protocol's
  challenge in `PaymentRequiredError`; set `Transport.Payment` to settle it,
  and the transport polls or retries afterwards. No payment protocol is
  built in.
- **`ResourceGuard`.** Each operation of a resource declares the least it
  needs (`AccessAgent`, `AccessPerson`, or `AccessAuth` with a scope). The
  guard verifies the presented token, challenges for the next one, and hands
  the verified `Caller` to the handler. An auth-token challenge also asks for
  the scope the agent already holds, so one auth token per resource keeps
  every grant.
- **Hosted agents in one call.** `agentprovider.Client.Enroll` enrolls a key
  at an agent provider and returns an `aauth.Agent` that keeps its tokens
  fresh.
- **The sandbox.** `aauth-sandbox` runs the agent provider, person server,
  access server and demo resources for all five access modes on
  `https://*.aauth.test`, locally or in Docker, with its own certificate
  authority, consent pages, a message trace, and a signing helper for
  clients that cannot sign, such as Postman and curl. The helper also signs
  as a request's own `Signature-Key` names, so generic clients need no
  sandbox headers. `--remote` swaps in
  another implementation of a role, and `--upstream` puts a resource of your
  own behind it. See the [sandbox guide](../guides/sandbox.md).
- **Walkthrough code.** `examples/walkthrough` has tested code for each step
  of the AAuth walkthroughs, for every role, marked as named regions that
  the PIDL walkthrough viewer shows next to the HTTP messages.

## Security

v0.3.0 closes several ways a party could act beyond what it was given.

- **Signatures are bound to the receiving server.** Servers and
  `ResourceGuard` refuse a request whose signed `@authority` is another
  host, so a server an agent calls cannot replay the request to another
  server. Use `RequestVerifyOptions.Authority` and `AuthorityOf` when you
  verify requests yourself.
- **Four-party resources take auth tokens only from their access server.**
  With `ResourceGuardConfig.Audience` set, an auth token must be issued by
  that access server, so a person server cannot skip it.
- **Agent identifiers belong to their provider.** An agent token's `sub`
  must be in the domain of its `iss`. `SelfSignedResolver` verifies only
  top-level agent tokens.
- **Consent covers what the person saw.** An agent cannot widen a request
  the person approved while an access server decides, and approvals fail
  with `ErrRequestChanged` when the request changed after it was shown.
- **Key discovery stays on the issuer.** `dwk` must be one of the four AAuth
  metadata documents, and redirects to another host are refused.
- **Bounded work for unauthenticated callers.** Verification reads at most
  4 MiB of a body, the JWKS cache resists floods of unknown issuers, stores
  are capped and pruned, and rate limits are kept per key space.
- **Less to learn from errors.** Responses carry fixed descriptions, not
  internal error text.
- **Interaction codes** are consumed at the person's authenticated decision,
  limited per client, and refused once expired. Pending URLs answer
  `410 Gone` after delivering their result.
- **Call chaining is opt-in** at the person server
  (`Config.AllowCallChaining`), and `ResourceGuard` can check revocation
  (`IsRevoked`) and passes the token's account and tenant to the handler.
- **The sandbox stays on your machine.** It listens on loopback by default;
  the signing helper returns redirects unchanged, answers only local
  clients, refuses browser requests, and signs only for the sandbox's hosts
  and upstreams; its CA is limited to the sandbox's names; and the image
  builds with Go 1.27.3.

## Fixes

- `ChainInteraction` and `WriteClarification` mark their 202 bodies as JSON.
- `aauth-sandbox serve` records its listener address before its first
  request, which could otherwise dial the default port.
